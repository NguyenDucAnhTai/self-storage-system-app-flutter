## Cross-cutting UX and contract audit

| Concern | Current evidence | Gap / requirement for Stitch and implementation review |
|---|---|---|
| Authentication/authorization | FE attaches stored bearer and retries 401. ZIP TODOs leave many security/role checks commented; production OAS leaves security empty on many endpoints | Treat signed-in as UI state only. Protected data/write screens must show session-expired/forbidden states. Do not represent endpoint presence as customer permission |
| Ownership and account switching | Auth controller invalidates dashboard and notifications on auth transitions | Verify every repository/cache is account-scoped; direct `customerId` query parameters must never choose another account. No live two-user isolation test exists |
| Loading/empty/errors | Reservation availability explicitly has loading, empty, error/retry; dashboard sections independent | Most new modules have no FE at all. Each proposed screen needs separate loading, valid empty, 400 validation, 401 expiry, 403 forbidden, 404 missing, 409 conflict, timeout/offline, retry and stale-state specs where relevant |
| Date/timezone | Reservation serializes local year/month/day as `YYYY-MM-DD`; stale responses rejected by request counter | Keep date-only semantics; don't append UTC timestamp or call `.toUtc()`. Test Bangkok timezone boundaries; production OAS date format is only `string`, so date semantics come from ZIP Zod/source and existing client tests |
| Double submit/stale status | Reservation has `_submitting`; payment tracker is bounded/cancellable | Ensure addendum, support, incident, inventory and refund actions get submit locks/idempotency behavior. Refresh current server state after 409 or uncertain timeout; don't blindly replay a write |
| QR/OTP privacy | No inventory request UX currently | Never write OTP, QR token, raw request envelope or full payment QR URL into analytics/logs/deep links. Obscure after expiry/one-time use and on screenshots |
| Payment truth | Current payment UI treats only `paid` as success; polls backend status | Do not generate mock success or infer from returning from banking app. Handle `pending`, `partially_paid`, `expired`, `cancelled`, network timeout and webhook delay |
| Cancellation/refund policy | ZIP reservation controller/service describes state-dependent 24h policy and internal refund request creation | Show server-calculated amount/state; do not calculate or promise refund independently. Confirm cancellation modal and bank-detail field schema before implementation |
| Two-party contract and check-in | Contract active requires staff side/check-in in source; check-in date shift can require customer re-sign | Customer UI must distinguish awaiting staff action, customer signature required, active, overdue and settlement. Don't claim active storage after customer click alone |
| Routes and navigation | Existing route list in API re-audit doc | Proposed screens must be clearly labeled proposed routes. No route currently exists for additions in this matrix |

## Priorities

- **P0 blockers:** confirm server auth/role/ownership and test-environment access; fix the known legacy contract-renew conflict before representing renewal as supported; verify reservation create/cancel and payment truth against the documented current service contract before E2E claims.
- **P1 essential:** customer payment history, addendums and settlement, reservation reassignment response, customer inventory request lifecycle, incidents, refund read-only status, amenity-selection parity; only after BE confirms role and ownership enforcement.
- **P2 optional:** support ticket UX refinements, richer dashboard analytics, convenience filters, and nonessential presentation polish.
