# Stitch Brief — Self Storage Customer Mobile

**Purpose:** Provide Stitch with the verified customer-facing information architecture, API-backed content and actual UI states. This is a design brief, not an implementation request. API audit source and conflicts are in [API-RE-AUDIT-2026-10-30.md](API-RE-AUDIT-2026-10-30.md); source/test/UX gaps are in [FLUTTER-CUSTOMER-GAP-MATRIX.md](FLUTTER-CUSTOMER-GAP-MATRIX.md).

## Design constraints

1. Design only the Customer Mobile experience. Staff, Facility Manager, Business Ops and System Admin actions do not belong in customer navigation.
2. Mark routes as **Existing** or **Proposed** below. Do not imply a proposed route is implemented.
3. Only design content supported by an API or current app source. Use loading/error/empty states explicitly; do not invent unit availability, time slots, reservations, payment success, inventory contents, refund amounts, contract status, support messages or notifications.
4. Reservation time slots come from a facility-and-date API; physical-unit availability is a separate API. The unit dropdown does not generate/check slots. Keep Create Reservation disabled until a returned valid slot and returned available physical unit are both selected.
5. Use exact current enum values where displayed. Unknown/future enum states must fall back to a neutral “Status update needed” detail, not be mapped to success.
6. Payment success means backend status `paid` only. Never create fake payment state, simulate a bank transfer, or present a generated QR as backend data.
7. Do not expose or log OTP/QR secrets. Raw OTP and pickup QR payloads are sensitive and time-limited.
8. Customer identity/ownership is a server-side authorization blocker. Avoid designing arbitrary customer-ID entry, cross-customer lookups, staff filters or admin selectors.
9. Separate no results from request failure. Every API-backed section needs a loading state, an accurate empty state, and API-specific errors/retry where retry is safe.

## Navigation recommendation

Keep existing bottom navigation as Home, Explore, My Bookings and Profile. Make contracts, notifications, payment history, inventory and support reachable from Home/profile or a storage section only after routes and API access are approved. Preserve current reservation routes. For new features, use nested detail routes proposed above and include a back path to the owning list. Do not add staff tabs or operational dashboards.
