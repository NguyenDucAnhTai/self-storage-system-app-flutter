# Flutter FE — Backend API Feature Gap Analysis

**Snapshot:** 2026-10-23 (Asia/Bangkok)  
**Evidence source:** public [Render Swagger UI](https://self-storage-system-be.onrender.com/api-docs/) and embedded `swagger-ui-init.js` OpenAPI document, fetched with GET only. OpenAPI **3.0.0**, declared production server `https://self-storage-system-be.onrender.com`, **149 operations / 21 tags**. No business API was called for this inventory.  
**Scope:** Flutter customer FE only. This is an API surface inventory, not a claim that every operation is safe or authorized for a customer.

## Reading the matrix

- Each HTTP operation in the retrieved `paths` object is listed once; endpoint descriptions are shortened to 170 characters where necessary.
- `Explicit security: []` means the operation explicitly declares no OpenAPI security requirement. `Inherits global (none declared)` means no operation-level security and no global security was defined. Neither proves an endpoint is public: documented 401/403 responses, observed auth behavior, and backend authorization blockers remain relevant. Schemes include bearer JWT and `accessToken` cookie, but no operation requirement is inferred where the spec omits it.
- Role is shown only when the operation description/tag text names a role. Otherwise it is **Unspecified by OpenAPI**; no role is guessed from route naming.
- FE “implemented” means a corresponding client call and customer flow were found in source. Tests are local/mocked. All live customer API behavior is **NOT VERIFIED** here.
- Do not use this matrix to invoke mutation operations against production. Reservation, payment, contract, inventory, notification, and admin writes require a permitted test environment and authorization.

## Key customer-facing gaps and blockers

1. **Customer dashboard:** `GET /customer-inventories/summary` is wired to the dashboard. Metrics/activity are parsed strictly from the response; unavailable/malformed data renders an error state, not fabricated zeros. This call has local mocked coverage only. Its OpenAPI operation has 401/403 responses while security annotations are incomplete; account scoping and authorization require BE verification.
2. **Inventory management:** customer SKU CRUD, inventory in/out/move/adjust, movement history, unit tree and SKU/barcode locations are present in the API surface but have no Flutter customer workflows. The dashboard summary does not implement those workflows.
3. **Payment history:** `GET /payments` is not used by the FE; dashboard does not create payment sessions. Implement history only after confirming customer filtering/ownership and authorization.
4. **Amenity discovery/selection:** APIs exist for facility amenity offerings and search-by-amenity. Current reservation request may leave amenities empty; selection UX and payload should be reconciled with confirmed schema/business rules.
5. **Contract lifecycle:** customer list/detail/sign/renew calls are present. Contract authorization remains a backend blocker recorded in `BACKEND-BLOCKERS.md`; no live contract is read or changed in this task.
6. **Operational APIs:** manager, staff, approval, audit, user and configuration operations are outside customer UI scope unless a product requirement explicitly adds a permitted role-based experience.
7. **No OpenAPI customer operations were found for support requests, reviews/ratings, promotions, access-control/key management, or realtime notification streams.** This is limited to this Swagger snapshot; it does not prove the wider product has no such capabilities.

## Authorization and safe verification

The OpenAPI defines bearer/cookie schemes but leaves global security unset and several operations explicitly use `security: []`, even when 401/403 responses are documented. Existing FE integration docs identify reservation/payment/contract auth TODOs. A shared FE bearer token interceptor does not resolve server-side ownership/role authorization. Until the BE team confirms protected customer routes and provides a permitted seeded test environment/account, live customer journey status remains **NOT VERIFIED / BLOCKED**, and production mutation routes must not be exercised.
